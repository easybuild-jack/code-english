# CodeEnglish 我的程序员英语翻译练习工具

## 需求背景文档

版本：V1.4
日期：2026-09-08

---

# 1. 背景

## 我是谁

一名做了多年开发的老程序员。英文能读，写不出来。日常开发已经离不开 AI 编程工具（Cursor、Claude Code、Codex 等），这些工具用英文沟通效果更好，我每天都要用英文跟它们说很多话，但经常是"知道意思，不知道行内怎么说"。

## 为什么现在做

每天和 AI Agent 对话，是一个现成的、高频的、不需要额外挤时间的英语输出场景。我不想再去下载一个背单词 App 然后三天后放弃，我想把练习放进本来就要做的事情里。

从"职业 + 行业"入手，是因为这是我每天真实使用的词汇和句子。学的就是用的，用的就是学的，不需要再学一遍。

## 现有翻译工具为什么不够

- 翻译不知道我是程序员、做什么行业，给的是字典上最泛的译法，不是同行真正在用的说法。
- 翻译完就复制粘贴，看都不看，用了几年英语一点没长进。

## 我要做什么

一个属于自己的、懂我背景的中英翻译工具。我用中文表达想法，它结合我的职业和行业给出准确、专业、忠实原意的英文翻译。我**看着翻译结果，自己把英文敲进各个对话框**。这个"手动敲"的动作就是练习。

这不是一个要卖的产品，只需要对我自己有用。

---

# 2. 核心理念

## 翻译是重点

工具只做一件事：把我的中文翻译成我这个圈子里真正在用的英文。不扩写、不替我思考、不帮我"优化 Prompt"。我说什么，它翻什么，专业性体现在选词和句式上，不体现在加内容上。

## 手动输入即练习

普通翻译软件：翻译 → 复制 → 粘贴。
CodeEnglish：翻译 → **对照着看** → **自己敲进对话框**。

每一次手动输入，都是一次拼写、语序、句型和专业词汇的练习。工具不出题、不批改，练习发生在我敲键盘的过程中。

由此确定几条原则：

- 翻译结果必须准确、专业、忠实原意，因为它是我抄写的范本。
- **不做一键复制按钮**。这是有意留下的摩擦，防止自己偷懒。
- 界面为"对照抄写"而优化：悬浮置顶、字体清晰、窗口小、不抢焦点。

# 3. 要解决的具体问题

## 问题 1：普通翻译不贴合技术场景

中文：

> 增加订单状态缓存，降低数据库压力。

普通翻译：

```
Add order status cache to reduce database pressure.
```

行内表达：

```
Add an order status cache to reduce database load.
```

区别在选词：行内说 `database load`，不说 `database pressure`。原文没有的信息，翻译里也不应该出现。

## 问题 2：翻译不了解我的职业与行业

同一个中文词，在不同背景下英文不同：

| 中文 | 电商后端 | 金融系统 | 前端 |
|---|---|---|---|
| 订单 | order | trade / deal | order |
| 服务 | service / microservice | service | service（多指 API 服务） |
| 上线 | release / deploy | go-live | ship / release |

工具需要知道我是谁、做什么行业、用什么技术栈，才能给出准确的译法。

## 问题 3：复制粘贴无法积累

普通翻译工具：

```
输入中文 → 复制英文 → 粘贴 → 结束，什么都没记住
```

CodeEnglish：

```
输入中文
↓
看翻译，看关键词讲解
↓
自己把英文敲进对话框
↓
顺手收藏生词和好句
↓
翻译历史自动成为练习记录
↓
形成我自己的技术英语库
```

# 4. 功能需求

# 4.1 专业背景翻译（核心）

将中文翻译成符合我职业与行业习惯的英文。翻译必须：

- **准确**：忠实原意，不增不减
- **专业**：使用该领域内实际通行的词汇和句式
- **可抄写**：长度和结构适中，方便对照手动输入

支持场景：

- 与 AI Agent 对话
- 代码注释、commit message、PR 描述
- 技术会议
- 邮件 / IM 沟通

例如，输入：

```
帮我重构这个服务
```

输出：

```
Please help me refactor this service.
```

而不是自行扩展成 `Please refactor this service while improving maintainability and reducing coupling.`（原文没有这些内容）。

## 输出内容

每次翻译提供：

- **翻译结果**：主输出，用于抄写
- **关键词汇标注**：哪些词是技术领域特有的选词、为什么选它（如 `load` 而非 `pressure`）
- **收藏入口**：可收藏其中的单词、短语或整句

---

# 4.2 背景配置

翻译准确的前提是知道我是谁。分两层：

## 我的档案（配置一次，长期生效）

作为每次翻译的常驻上下文，放在配置文件或设置页里。当前值：

- 职业：程序员
- 技术栈：Java 全栈（Java / Spring 后端 + 前端）
- 行业：按实际项目填写，可留空

配置项保留可改，换项目时调整行业即可。

## 场景（每次可切换）

决定语气和选词范围，默认「工作」：

- **工作**（核心场景）：写代码、对 AI 编程助手下指令、描述需求和 Bug、注释、commit message、PR 描述。指令式，简洁直接，用技术圈通行词汇
- **职场**：会议、汇报、邮件、和同事沟通，礼貌完整
- **日常**：闲聊、约时间、问路，自然口语
- **购物**：点餐、咨询客服、询价、退换货，简短实用
- **旅行**：机场、酒店、交通、求助，一听就懂

生活场景不要求技术词汇，关键词改为挑地道说法和固定搭配。场景是翻译的一个参数，不是独立功能。

## 模式：翻译 / Ask

- **翻译**（默认）：只做翻译。用户发来的任何内容都当作待翻译文本，哪怕像个问题或指令，也不回答不执行。这样练习时不会被模型"顺手帮忙"打断
- **Ask**：翻译完有疑问时切过去问一句，比如"为什么不用 function"。相当于随手能问的英语老师，多轮对话，只在内存里，不进历史
- Ask 有明确边界：只回答英语学习问题（单词用法、地道说法、语法、发音、纠错、表达差异），其他一律拒绝，固定回一句「这里只聊英语学习相关的问题。」。这个工具不是通用聊天窗口，越界的事去问 Cursor

## 翻译 Prompt 初稿

档案和场景最终都会拼进这个 system prompt。以下为初稿，接上模型后用下面的样例句对照验证再调。

```
你是一名资深 Java 全栈工程师，同时是英语母语者。
用户是一名中文程序员，技术栈为 Java / Spring 后端 + 前端。
{行业不为空时追加：用户所在行业为 <行业>。}
当前场景：<工作 | 职场 | 日常 | 购物 | 旅行>。<该场景的描述、语气和选词要求>

把用户的中文翻译成英文，要求：
1. 忠实原意，不增加原文没有的信息，不扩写，不解释。
2. 用该场景下母语者实际会说的词汇和句式，不字面直译。
   「工作」时用 Java / Spring / Web 前端圈子里通行的词汇，简洁的指令式语气；
   「职场」时礼貌完整；「日常 / 购物 / 旅行」时用地道口语。
4. 输出格式：
   翻译：<英文>
   关键词：<1~3 个技术选词，各一句话说明为什么选它>
```

## 验证样例（场景：工作）

这些是设计阶段的预期输出，用来检验模型是否做到"懂背景、不加戏"。任何一个模型跑出来明显偏离，就说明 Prompt 或模型需要调整。

| 中文 | 预期翻译 | 关键词 |
|---|---|---|
| 把这个接口改成分页返回 | Make this endpoint return paginated results. | `endpoint`：对 AI 说"接口"用 endpoint，`interface` 会被理解成 Java 接口 |
| 这个 Service 里的事务没生效，帮我看看 | The transaction in this service isn't taking effect. Can you take a look? | `isn't taking effect`：比 `doesn't work` 更准确地表达"配了但没起作用" |
| 加个全局异常处理，统一返回格式 | Add a global exception handler with a unified response format. | `global exception handler`：Spring 圈子固定说法，对应 `@ControllerAdvice` |
| 前端这个表单提交后要清空 | Reset the form after submission. | `reset` 而非 `clear`：前端表单场景惯用 reset |
| 把这段查询改成用 MyBatis 的动态 SQL | Rewrite this query using MyBatis dynamic SQL. | `rewrite`：改写现有代码，比 `change` 具体 |
| 这个方法要保证幂等 | This method must be idempotent. | `idempotent`：幂等的唯一标准译法 |

检验标准：

- 没有加原文没有的内容
- 长度一行以内，适合抄写
- 每句至少有 1 个值得收藏的技术选词
- 口语（"帮我看看"）翻成行内说法（`Can you take a look?`），而不是字面直译（`Please help me check it`）

# 4.4 收藏与积累

可以收藏：

- 单词
- 短语 / 技术表达
- 整句

例如：

```
idempotent

中文：幂等
领域：API Design
例句：This API should be idempotent.
```

积累方式分两种：

- **主动收藏**：点击收藏
- **自动记录**：翻译历史本身就是练习记录。一个词或句型出现过几次自动统计，下次翻译时能看到"这个词你已经敲过 3 次"

支持：

- 收藏列表按类型、领域筛选
- 出现次数统计
- 熟练度标记（手动标"已掌握"）

# 4.5 桌面悬浮窗口

- Windows 桌面应用（一期）。我另有一台 mac，macOS 版本后续再做，一期技术选择不能堵死这条路
- 始终置顶
- 快捷键唤醒
- 不影响开发流程

## 设计目标：方便对照抄写

典型姿势：悬浮窗贴在 Cursor 对话框旁边，一边看翻译一边往 Cursor 里敲英文。因此：

- 窗口小，不遮挡目标对话框
- 翻译结果字体清晰，关键词高亮
- 输入英文时不抢焦点
- 没有一键复制按钮

使用场景：

```
我在 Cursor 里想说："把这个接口的返回值改成分页结构"
↓
唤起 CodeEnglish，输入中文
↓
看到：Change the return type of this endpoint to a paginated structure.
     关键词：endpoint（接口，AI 语境下比 interface 更准确）
             paginated（分页的）
↓
对照着，手动敲进 Cursor 对话框
↓
顺手收藏 paginated
```

# 6. 技术方案

## 桌面端

Tauri。

原因：

- 一套代码同时编译 Windows 和 macOS
- 轻量、低资源占用
- 支持窗口置顶、托盘 / 菜单栏、全局快捷键、开机自启，两个平台都有官方插件
- 适合长期运行

技术：

```
Tauri 2
Vue3 + TypeScript
Rust Backend
```

## 为 macOS 扩展预留的约定

一期只做 Windows，但下面这些选择零成本，从一开始就照做，后续编 mac 包时不用改代码：

- 快捷键用 `CmdOrCtrl` 修饰键定义，Windows 映射 Ctrl、macOS 映射 Cmd
- API Key 用 `keyring` crate 存入系统钥匙串（Windows 凭据管理器 / macOS Keychain），不自己实现加密，不用 DPAPI 等 Windows 专属 API
- 字体全部用系统字体栈，不打包字体文件
- 朗读走在线词典接口，不依赖任何平台的系统语音
- 文件路径、数据目录用 Tauri 的跨平台 API 取，不写死 Windows 路径

## AI 服务：多模型可切换

第一期只对接一个模型，但从一开始就按多模型设计，后续加模型只加配置和适配器，不动业务代码。

### 目标支持的模型

云端：

- DeepSeek
- 豆包（火山方舟）
- ChatGPT（OpenAI）
- Claude
- Gemini
- 通义千问

本地：

- Ollama（Qwen / DeepSeek 等本地模型）

用自己的 API Key。涉及公司业务信息时切到本地模型。

### 扩展设计

**1. 统一的模型接口（Rust 侧）**

业务层只依赖一个 trait，不知道底下是哪家：

```rust
#[async_trait]
pub trait LlmProvider {
    fn id(&self) -> &str;                      // "deepseek" / "doubao" / "openai" ...
    fn display_name(&self) -> &str;
    async fn chat(&self, req: ChatRequest) -> Result<ChatResponse>;
    async fn chat_stream(&self, req: ChatRequest) -> Result<ChatStream>;  // 二期
    async fn test_connection(&self) -> Result<()>; // 设置页"测试连接"
}
```

`ChatRequest` 只包含 system prompt、user message、temperature 等通用字段，不带任何厂商私有参数。

**2. 一个 OpenAI 兼容适配器覆盖大部分厂商**

DeepSeek、豆包、通义千问、Ollama 都提供 OpenAI 兼容的 `/v1/chat/completions` 接口，只是 `base_url`、`api_key`、`model` 不同。因此实际只需要：

- `OpenAiCompatibleProvider`：一份实现，通过配置区分厂商（覆盖 OpenAI / DeepSeek / 豆包 / 通义 / Ollama）
- `AnthropicProvider`：Claude 的接口格式不同，单独实现
- `GeminiProvider`：Gemini 接口格式不同，单独实现

第一期只写 `OpenAiCompatibleProvider` 一份代码，就已经能接 DeepSeek 和豆包，只差配置。

**3. 模型配置表 `llm_providers`**

每个模型一条记录，在设置页增删改：

- id（唯一标识）
- 显示名称
- 类型（openai_compatible / anthropic / gemini）
- base_url
- api_key（本地加密存储）
- model（模型名，如 `deepseek-v4-flash`、`doubao-pro-32k`）
- 是否启用
- 是否默认

**4. 前端切换**

悬浮窗顶部一个下拉框，列出已启用的模型，切换后立即生效，并记住上次选择。翻译历史里记录本次用的是哪个模型，方便对比不同模型的翻译质量。

**5. 内置预设**

首次使用时预置几家的 `base_url` 和默认 `model`，只需填 API Key：

| 预设 | base_url | 默认 model |
|---|---|---|
| DeepSeek | `https://api.deepseek.com/v1` | `deepseek-v4-flash` |
| 豆包 | `https://ark.cn-beijing.volces.com/api/v3` | 按控制台接入点填写 |
| OpenAI | `https://api.openai.com/v1` | `gpt-4o-mini` |
| Ollama | `http://localhost:11434/v1` | `qwen2.5:7b` |

**第一期对接：DeepSeek**（OpenAI 兼容、便宜、中文理解好）。豆包和 ChatGPT 二期只加预设配置即可。

DeepSeek 备注：`deepseek-chat` / `deepseek-reasoner` 已于 2026-07-24 下线，现只有 `deepseek-v4-flash`（便宜）和 `deepseek-v4-pro`（约 3 倍价）。翻译不需要推理，用 flash；且 V4 默认开思考模式，请求里要带 `"thinking": {"type": "disabled"}`，否则又慢又贵。这是 DeepSeek 私有参数，只对 deepseek.com 下发。

SQLite。

# 7. 开发规划

## 第一阶段：能用起来

周期：2~4 周。

按优先级：

1. 背景配置（职业 / 技术栈 / 行业）
2. 模型接入：按 `LlmProvider` 接口实现 `OpenAiCompatibleProvider`，只对接 DeepSeek，设置页可填 Key 并测试连接
3. 专业背景翻译（翻译结果 + 关键词标注），用 4.2 的样例句验证 Prompt
4. 桌面悬浮窗（为对照抄写优化）
5. 收藏（单词 / 短语 / 句子）
6. 场景切换（作为翻译参数）
7. TTS 朗读

一期只出 Windows 包，数据只存本机。

## 第二阶段：用顺手

- 多模型切换：加豆包、ChatGPT 预设，悬浮窗加模型下拉框
- 流式输出
- 剪贴板监听（复制中文后自动翻译）
- 翻译历史中的词汇出现次数统计
- 熟练度管理

## 第三阶段：mac 与进步可见

- macOS 版本（同一代码库编译）
- 两台电脑之间的数据同步方案
- 累计抄写了多少词、多少句、哪些领域的简单统计
- 视实际使用情况再决定要不要做编辑器插件
